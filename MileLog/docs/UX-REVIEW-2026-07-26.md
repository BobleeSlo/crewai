# MileLog UX/Usability Review — Audit & Fix Record

**Date started:** 2026-07-26
**Scope:** Every SwiftUI view under `MileLog/MileLog/Views/` plus `MileLogApp.swift`, `RootTabView.swift`
**Trigger:** User request to have a "critical agent, normally iOS user" test all features in the iOS Simulator, score UX/usability/user-friendliness, and iterate fixes until the score exceeds 95%.

## Important methodology note — read before trusting any score below

**This is NOT hands-on iOS Simulator testing.** This session runs in a Linux container with no macOS, no Xcode, and no iOS Simulator available — there is no way to actually launch MileLog, tap through its screens, or see it render. The user was told this explicitly and chose to proceed with the best available alternative: a rigorous **code-based UX review**, where an independent reviewer agent reads every SwiftUI view's actual source, traces realistic user journeys line-by-line, and evaluates against iOS Human Interface Guidelines and general usability heuristics (clarity, feedback, error prevention/recovery, consistency, accessibility, discoverability, copy quality).

This catches real, verifiable issues — missing loading/empty/error states, confusing copy, inconsistent patterns between screens, accessibility gaps (Dynamic Type, VoiceOver labels, tap targets), destructive actions without confirmation, and similar — all of which are visible directly in the SwiftUI declarations. It **cannot** catch issues that only manifest at runtime: actual layout overflow, animation glitches, real device performance, exact visual spacing/alignment, or how something *feels* to actually use. Before shipping, this app should still be built and tested in Xcode on a real Mac/device.

Same scoring rubric style as the Phase 17 correctness loop, adapted for UX severity: start at 100, subtract per confirmed finding — **−15 Critical** (blocks or fundamentally breaks a core task), **−8 High** (significant confusion/friction in a common flow), **−4 Medium** (noticeable friction, edge-case confusion, or a real accessibility gap), **−1.5 Low** (minor polish, inconsistent-but-not-confusing).

## Round 1 review: Score 23/100

A first reviewer, briefed explicitly on the no-simulator constraint above, read every view file top to bottom and traced ten realistic user journeys through the actual SwiftUI source. It found genuine, verifiable usability problems — this app's engineering effort to date went almost entirely into data correctness/compliance (see the separate Phase 17 audit, closed at 100/100), and UX polish had not yet had a dedicated pass.

### Critical

1. **Recording a trip failed completely and silently when location permission was denied — the single most core task in the app.** `LocationManager.start()` set `isTracking = true` unconditionally with no authorization check; `didFailWithError` was an explicit no-op ("Surfaced silently in the MVP"); and the one on-screen clue (`permissionHint`) was gated to disappear the instant the user tapped Start, regardless of whether permission was ever granted. The screen showed a fully "live"-looking recording (pulsing dot, ticking Stop button) that would sit at 0.0 km forever, ending in a blank, GPS-less trip handed to Classify with zero indication anything had gone wrong. **Fixed**: `LocationManager` now exposes the actual `CLAuthorizationStatus` (not just a coarse Bool), `start()` refuses to begin at all when not authorized, the Start button is disabled and visibly dimmed in that state (Stop remains available regardless, in case permission is revoked mid-recording), and the permission hint now stays visible for as long as the real blocker exists, with status-aware copy and a direct "Open Settings" deep link once actually denied.

### High

2. **A brand-new account with zero vehicles hit a guided dead end.** `VehiclesView` rendered a completely blank list under the "Vehicles" title with no explanation — the only affordance was a small, unlabeled "+" — while `RecordTripView`'s Start button was silently disabled with no text explaining why. **Fixed**: added a proper empty state (icon, gradient, explanatory copy, prominent "Add vehicle" button), matching `TripsListView`'s already-good pattern.
3. **Receipts uploaded and persisted automatically with no user review step, directly contradicting the code's own stated intent.** The comment claimed "the user can review the auto-filled amount... before tapping the next action," but OCR ran straight into an automatic upload with no intervening interaction — whatever OCR guessed (or failed to guess) was saved immediately, with no way to edit afterward. **Fixed**: added an actual review step — after OCR, the photo/type/amount are held pending or a photo/type/amount card is shown with editable fields and the OCR result as a checkable hint, with explicit "Discard"/"Save receipt" actions. Nothing uploads until the user taps Save.
4. **The soft-archive-vs-hard-delete distinction never reached the user, due to dead code.** `VehicleEditView`'s delete flow computed a `deletionMessage` ("Vehicle archived..." / "Vehicle deleted.") that was never rendered anywhere — the sheet just dismissed after a 0.3s delay with nothing shown. **Fixed**: the message now actually displays (checkmark + text overlay) before the sheet dismisses, with the delay extended to 0.9s so it's actually readable.
5. **A newly-recorded, unsaved GPS trip could be permanently discarded via one unconfirmed tap**, directly undermining a swipe-gesture protection added for the identical risk. `RecordTripView`'s classify sheet has `.interactiveDismissDisabled()` specifically because "an ordinary swipe-down gesture would otherwise discard a fully GPS-measured trip with no confirmation" — but the sheet's own toolbar "Discard" button offered the exact same unrecoverable loss with zero confirmation dialog. **Fixed**: Discard now shows a confirmation dialog before dismissing.

### Medium

6. Vehicle swipe-to-delete had zero confirmation and no after-the-fact explanation, unlike the dedicated in-sheet delete flow which explains the archive-vs-delete distinction — the identical destructive action had two very different levels of disclosure depending on which control was used. **Fixed**: swipe-to-delete now shows the same confirmation dialog and explanation.
7. The locked-entry banner told the user "Mileage, date and vehicle can no longer be edited" but Type is also disabled (added in an earlier compliance round specifically because it drives the reimbursement amount) — the banner copy was never updated. **Fixed**.
8. Missing `accessibilityLabel`s on four icon-only controls (Vehicles' "+", Detection Log's "⋯" menu, Report Selection's filter menu, `PrettyStepper`'s minus/plus buttons) — VoiceOver had nothing but a raw SF Symbol name to announce. **Fixed**: added descriptive labels to all four.
9. `PrettyStepper`'s minus/plus buttons were 38×32pt, below Apple's 44×44pt minimum tap-target recommendation, used for settings in an app whose premise is being operated while getting in and out of a car. **Fixed**: enlarged to 44×44pt.
10. **Not fixed this round (deliberately deferred)**: no dedicated priming screen precedes any system permission prompt (location, notifications) — only the bare OS dialog, with no MileLog-authored explanation of benefit first. This is a genuine onboarding-design gap, but fixing it properly means designing and building new screens, not a targeted code fix — flagged for a future round rather than rushed.
11. **Not fixed this round (deliberately deferred)**: a classify-notification tap that silently fails (trip merged back into an ongoing drive, or locked before the tap was processed) leaves its only trace in Settings → Detection Log, which an ordinary user has no reason to ever open. A proper fix needs a genuinely user-facing feedback mechanism (e.g. a follow-up notification), which is more scope than a quick fix — documented for a future round.

### Low

12. The inline GPS route map (`TripMapView`) was fully non-interactive with no way to zoom/pan to verify a route on what may be a tax-relevant record. **Fixed**: the inline preview stays non-interactive (avoids fighting the surrounding Form's scroll gesture), but tapping it now opens a full-screen, fully interactive map.
13. Settings' "Grant location permission" button was a guaranteed no-op once permission was actually denied (`requestEnable()` just logs a warning nobody sees; iOS never re-shows a system prompt after denial) — it looked identically actionable in every state but silently did nothing in the one state a user is most likely to be stuck in. **Fixed**: now shows an "Open Settings" deep-link button instead, once actually denied.
14. **Not fixed this round (deliberately deferred)**: no reminder exists for a manual trip left recording for hours — unlike auto-detect's careful stationary-timeout handling, the manual hero badge just keeps ticking indefinitely. Low-value/narrow enough to defer.
15. **Not fixed this round (deliberately deferred)**: `AuthView`/`VehicleEditView`'s disabled primary buttons (empty password / empty vehicle name) give no inline explanation beyond a static placeholder hint. Minor, deferred in favor of higher-value fixes this round.

### What already worked well (per the reviewer, kept as-is)

`TripsListView`'s empty state, `TripEditor`'s locked-entry banner and stale-data alerts, `VehicleEditView`'s locked-fields footer copy, the Face ID/Touch ID enablement flow, the Bluetooth-pairing error copy, the bilingual `InfoPlist.xcstrings` usage-description strings, and the Record tab's live-feedback hero badge were all called out as genuinely good UX and left untouched.

## Round 2 review: Score 65/100

A second reviewer verified round 1's fixes in detail (found no Critical regressions — see below) and continued the broad sweep into screens not yet deeply examined: auth, settings end to end, trip detail viewing, the report-generation flow, and Detection Log readability.

### High

1. **Swipe-to-delete on a trip had zero confirmation and was instant/permanent — a real regression relative to the protection round 1 just gave vehicles for the identical gesture.** A trip is the app's actual core record (GPS-measured, possibly already-classified for tax purposes) and is strictly harder to recreate than a vehicle entry, yet had *less* protection. **Fixed**: swipe-to-delete on a trip now shows a confirmation dialog before actually deleting, matching the pattern round 1 established for vehicles.

### Medium

2. `ReceiptsSection`'s "Discard" button didn't clear a stale upload-failure message, leaving a false "Couldn't save the receipt" error on screen indefinitely after the user had already abandoned that receipt. **Fixed**: Discard now also clears the error.
3. The vehicle-deletion confirmation overlay (round 1) was a small centered card, not a blocking scrim — the Form's fields and buttons stayed live and tappable underneath for the full delay before the sheet dismissed, so a stray tap could re-open the same confirmation on an already-mid-teardown vehicle. **Fixed**: the whole form is now disabled for the duration of that window.
4. PDF report generation could fail completely silently while still looking successful — both generators swallowed a file-write error and returned a "successful" result regardless, so the user could tap Share on a broken/missing file for what's often the actual tax deliverable they're about to hand an accountant. **Fixed**: both generators now return `nil` on a write failure, and the report-selection screen shows a plain-language error instead of a broken share button.
5. Raw SDK/network error text reached the user in two places, including the app's front door: `AuthView`'s sign-in/sign-up failures showed `error.localizedDescription` directly, and `ReceiptsSection`'s upload failure did the same. **Fixed**: both now map to plain-language copy (wrong password, already-registered, network trouble, etc., with a sensible fallback).

### Low

6. `RecordTripView`'s auto-detect status told the user to "open Settings" during the genuinely-reachable "permission not yet asked" state — wrong, since iOS won't show a Location entry for an app it's never asked yet. **Fixed**: split from the "already granted When-in-Use, needs upgrade to Always" case, matching `SettingsView`'s own already-correct copy for this state.
7. Two Potni Nalog settings fields ("Koristnik po nalogu", "Na relaciji") were the only inputs in that section with no English gloss, breaking the bilingual pattern every sibling field established. **Fixed**: added "(beneficiary)"/"(area/route)" glosses.
8. Detection Log entries referenced only a truncated UUID, giving no way to tell which actual trip/drive an entry was about even to someone who does open that screen. **Fixed**: entries now reference the trip's own start date/time where that data is available.
9. **Not fixed this round (deliberately deferred)**: `TripDetailView` has no distinct read-only "view" mode — tapping any trip to just check its details drops straight into a fully live, editable form. A locked trip is protected field-by-field, but an unlocked trip (the common case for up to `lockAfterDays`) has no friction between browsing and editing. A proper fix means designing an actual view/edit mode distinction, not a quick patch — flagged for a future round.

### Confirmed correct from round 1

The reviewer traced round 1's fix areas in detail and found no Critical/High regressions: the permission-state modeling (`authorized`/`permission` kept in lockstep, correctly gating Start but never Stop, with no exploitable "quick tap during request" race) held up; `ReceiptsSection`'s pending-review flow correctly keeps the Add-photo button and the review UI mutually exclusive with no double-input state (aside from the stale-error gap fixed above); `VehiclesView`'s per-vehicle-sheet state correctly resets on re-presentation (SwiftUI tears down and rebuilds `@State` for each `.sheet(item:)` presentation); and `TripEditor`'s full-screen map, Discard confirmation, and existing staleness alerts are all correctly mutually exclusive with no double-dialog path.

## Round 3 review: Score 62/100

A third reviewer verified rounds 1-2's fixes (no Critical regressions, one real Medium-severity gap found — see below) and swept navigation, Settings end to end, Bluetooth pairing, and async-operation feedback with fresh eyes.

### High

1. **Reinstalling the app, or signing into an existing account on a new device, injected a phantom duplicate vehicle into the user's permanent cloud records — and could misattribute the very next trip to it.** `Store.init()` unconditionally seeded a placeholder "My car" vehicle whenever local storage was empty — true not just for a genuinely new account, but for *any* fresh install/new-device sign-in into an *existing* account, since local JSON files don't exist yet on a new device regardless of how much real history the account already has. `initialSync` pushes local vehicles to Supabase *before* pulling the cloud ones down, so this seed got permanently written into the user's real cloud vehicle list — indistinguishable from a real vehicle — before their actual vehicles ever arrived. If the user started a trip immediately after setting up the new phone, it could get attributed to this junk vehicle. **Fixed**: removed the auto-seed entirely. There's no reliable way to distinguish "new account" from "existing account, new device" from local disk state alone, so the safe fix is to never guess — round 1's Vehicles empty state already gives a genuinely new user a clear, one-tap path to add their own vehicle with their own name/plate.
2. **No sync/loading indicator anywhere while the initial sync runs, so a slow-network first sign-in on a new device showed a confident "no data" UI instead of "loading."** A user restoring an account with months of history, on a slow connection, would see the cheerful "No trips yet" / "No vehicles yet" empty states while their actual history was still downloading — a genuinely alarming false signal for what's meant to be a defensible tax record. **Fixed**: `Store` now exposes `isSyncing`, correctly scoped against overlapping sync calls via the existing generation-guard pattern; `TripsListView`/`VehiclesView` show a "Syncing…" state instead of the empty state while a sync that hasn't yet produced any data is in flight.

### Medium

3. Settings' Energy Mode footer promised "changes take effect on the next trip start" — factually wrong. The mode change applies immediately to the live `CLLocationManager`, and `TripDetector` reads the accuracy threshold live inside its per-GPS-fix callbacks, so switching modes mid-drive immediately changes which fixes get accepted into a trip already recording. **Fixed**: corrected the copy.
4. The trip swipe-delete confirmation (round 2) could be bypassed by the very lock protection it's supposed to respect: it re-validated `isLocked` against a stale snapshot captured at swipe time, not a live lookup — if the trip crossed the lock threshold while the confirmation dialog stayed open (e.g. the app was backgrounded/foregrounded, re-running the automatic lock sweep), tapping Delete would remove the now-locked trip anyway. **Fixed**: the delete action now re-fetches the live trip by id before deleting, so `Store.deleteTrips`'s own lock check sees current state.
5. `AuthView`'s friendly-error mapping (round 2) matched any error containing "password" to a hardcoded "needs 6 characters" message — but Supabase's actual password policy is server-configurable independent of this app's local check, so a different password-related rejection could get the same, possibly wrong, canned explanation. **Fixed**: narrowed the match to require an actual length/strength signal alongside "password."
6. PDF "Generate" gave zero loading feedback for what's a fully synchronous, main-thread render — a heavier logbook could visibly stall the UI with no reassurance anything was happening. **Fixed**: the button now shows a spinner and disables itself during generation (true background generation wasn't attempted, since the report generators can call back into main-actor-isolated Store lookups).

### Low

7. The vehicle-deletion success overlay's `.disabled()` (round 2) didn't reach the toolbar's Save/Cancel buttons — toolbar content isn't a descendant of the Form it was applied to — so a stray tap could still prematurely dismiss the confirmation. **Fixed**: Save/Cancel are now explicitly disabled too during that window.
8. "Apply locks now" acted with zero outcome feedback for a compliance-relevant action. **Fixed**: now reports how many trips were actually locked.
9. **Not fixed this round (deliberately deferred)**: `CameraImagePicker` silently substitutes the photo library when no camera is available, with no on-screen indication — narrow real-world reachability (every iPhone has a camera; only unusual hardware would trigger this).
10. **Not fixed this round (deliberately deferred)**: no warning when pairing a Bluetooth device already paired to another vehicle. `TripDetector`'s matching already defensively handles the resulting ambiguity rather than silently guessing wrong, so this is a missed heads-up, not a correctness risk — lower priority than this round's other findings.

### Confirmed correct from rounds 1-2

Verified in detail: the trip swipe-delete dialog correctly targets the right trip even if `store.monthSections` reshuffles while it's open (it holds the actual `Trip` value, and deletion is by id against live state) — the only real gap was the lock-status staleness fixed above. `ReportSelectionView`'s `generationFailed`/`result` reset symmetry is fully correct — every place either is mutated resets both together. `VehiclesView`'s form-disabling during the delete overlay is correctly scoped to the form itself and doesn't get stuck, but (as fixed above) didn't originally reach the toolbar. `AuthView`'s friendly-error mapping is a clear improvement for the cases it targets, with the one over-broad match narrowed above.

## Round 4 review: Score 66/100

A fourth reviewer verified round 3's fixes (all confirmed correct — see below) and found that the two remaining weak areas were ground not yet walked: the manual-recording path's background-execution story, and the first-five-minutes experience for a user with nothing set up yet. Both of this round's top findings required tracing across files rather than surface-level inspection.

### Critical

1. **Manual Start/Stop recording never enabled background location, so an ordinary phone auto-lock silently truncated — or lost — the trip.** `LocationManager` never set `allowsBackgroundLocationUpdates = true`, while `TripDetector`'s automatic path sets it at all four of its own start sites, precisely because (per this repo's own tracking audit) iOS only grants sustained background runtime to apps using that flag with active location updates. So the manual recorder stopped accumulating distance the moment the phone locked or the user switched apps — i.e. during most of any real drive — on a screen whose live hero badge is explicitly designed to be glanced at while driving, with no warning anywhere and no way to recover the trip afterward. Note this is materially broader than the *crash*-persistence gap the correctness loop had already accepted as deferred: that one needed a process kill, this one needs only the screen to lock. **Fixed**: `start()` now enables background location updates (and re-applies the current energy preset, since `pausesLocationUpdatesAutomatically` decides whether iOS may silently stop updates mid-trip); `stop()`/`discardIfTracking()` hand the privilege back when the recording actually ends.

### High

2. **A brand-new account lands on the Record tab with zero vehicles and no explanation, and auto-detect silently discards a fully verified real drive in that state.** Record — not Vehicles — is the first screen after sign-in, and with no vehicles the vehicle menu is empty and Start is disabled with nothing but a dim to explain why. Worse, if the user toggles auto-detect on first (it's the very first control on that same screen), `TripDetector.finishVerification` drops a GPS/motion-verified drive outright, logging only to a Settings screen a first-time user will never open. **Fixed** on both paths: Record now shows an explanatory hint with an "Add vehicle" button that presents the vehicle editor directly, and a new notification tells the user when a detected drive couldn't be saved for lack of a vehicle. Also closed a gap in this fix itself: `selectedVehicleID` was only ever set in `onAppear`, so adding a first vehicle from the sheet would have left Start *still* disabled — an `onChange` now keeps the selection valid as vehicles are added, synced, or archived.

### Medium

3. The syncing state had no acknowledgement of a slow-but-alive connection — exactly the user it exists for (setting up a new phone, often travelling) could sit on a bare spinner indefinitely. **Fixed**: after 12 seconds the trips list adds a "taking longer than usual — your trips are safe" message. Deliberately does not cancel anything; the sync keeps retrying.
4. `VehicleEditView`'s Potni Nalog fields repeated the exact localization gap round 2 fixed on the Settings screen — "Vrsta in tip vozila" and "Število sedežev" were pure Slovenian inside otherwise-English chrome. **Fixed**: added English glosses, matching the pattern already established.

### Low

5. "Company location (mesto)" paired an English label with an untranslated Slovenian word, the reverse of the established gloss direction. **Fixed**: now simply "Company city."
6. Settings' About section named the backend vendor ("Supabase cloud") to a non-technical user — the same class of issue round 2 removed from the sign-up screen. **Fixed**: now "Private cloud backup."

### Confirmed correct from round 3 (round 4's own verification)

All four verification targets held up. The vehicle auto-seed removal introduced no memory-safety regression — every path was traced for empty `store.vehicles` and found to use optional chaining or explicit guards, never a force-unwrap (the real gaps it left were UX-level, fixed above as finding #2). The `isSyncing` flag cannot get stuck: its `defer` runs on every exit path including early `guard` returns and cancellation, so only an `await` that never returns at all could strand it, and no such call exists. The syncing-state branches are logically sound. `ReportSelectionView`'s `isGenerating`/`Task.yield()` pattern has no stale-capture or glitch — `selectedTrips` is a computed property re-evaluated after the yield, and the synchronous generator blocks the main thread thereafter, leaving no window for a mismatch.

## Round 5 review: Score 26/100

A fifth reviewer swept ground no prior round had walked — account recovery, sync *failure* (as opposed to sync *in progress*), receipts persistence, and the interaction between the two recorders. The sharp score drop is not a regression signal: rounds 1–3's fixes all held. But two of round 4's own fixes turned out to have real defects, which is exactly what an independent adversarial pass is for.

### High

1. **Round 4's no-vehicle notification created a re-alerting loop and never stopped GPS.** The new `guard let vehicle else { … }` in `finishVerification` notified and returned — but unlike the sibling FAILED branch a few lines below, it tore nothing down. Since `candidate` had just been cleared, the next GPS fix restarted verification, passed early on the first fix above 25 km/h, and dropped again: a banner every few seconds for the whole drive, with continuous GPS and CoreMotion running and background updates held. **Fixed**: the no-vehicle path now performs the same `motion.stop()` / `stopUpdatingLocation()` teardown as the FAILED branch, and the alert is limited to once per "user still has no vehicle" spell via a flag reset in `startMonitoring()`.
2. **Manual and automatic recording could run simultaneously, with the manual Stop button hidden.** `handleSignificantLocation` refuses to arm verification while a manual recording is running, but nothing re-checked ~90s later at commit time, and `LocationManager.start()` only refuses when a trip is already *active* — a pending candidate doesn't stop it. Both recorders could end up live on one drive, and because Record renders its Stop button as `if !autoActive`, the manual recording's only stop control vanished the moment the auto trip committed — leaving it running until the same drive was saved twice, double-counting km in a tax report. **Fixed**: `finishVerification` now yields to an in-progress manual recording (the user's explicit tap wins) and tears down cleanly.
3. **A failed initial sync landed on "No trips yet" with no error and no way to retry.** Every failure is `try?`-swallowed, and `initialSync` is called from exactly one place — on sign-in only — with no `.refreshable` anywhere in the app. A user restoring their account on a bad connection was told to "record your first trip," about years of tax records, until they force-quit. Round 3 fixed the *still-loading* half of this exact scenario; the *failed* half landed on the same false signal. **Fixed**: `Store` now tracks whether the download half succeeded (`lastSyncFailed`), both list screens show a "Couldn't load your trips/vehicles — they're safe" state with a Try again button, and pull-to-refresh now works on both.
4. **No password recovery anywhere.** A forgotten password — most likely exactly when the sign-in screen reappears, i.e. a new device or expired session — permanently locked the user out of their entire history. **Fixed**: added `sendPasswordReset` and a "Forgot password?" action, with confirmation copy deliberately phrased so it doesn't leak whether an account exists for a given address.
5. **Deleting a receipt didn't delete it.** Swipe-to-delete only mutated the local array (the code said as much: "Supabase row deletion can be added later"), and `TripEditor` re-pulls receipts on every appearance — so the receipt reappeared and stayed attached to the record. It was also the last destructive action in the app with no confirmation. **Fixed**: added a real `deleteReceipt` (row delete throws, photo cleanup best-effort) plus the missing confirmation dialog.

### Medium

6. **Round 4's `onChange` could silently re-attribute an in-flight recording.** Archiving the car you're currently recording from another tab would repoint `selectedVehicleID`, and `finalizeTrip()` reads it at save time — filing the drive against a different vehicle, uncorrectable in place since the selector is disabled while tracking. Own-car vs company-car is exactly what decides reimbursement. **Fixed**: the reassignment is now skipped while a recording is in flight.
7. **Signing out didn't stop tracking.** Sign-out discarded the in-flight trip but left significant-location monitoring running under no account — burning battery, emitting "Trip ended" notifications for drives recorded against nobody, and those trips then silently wiped if a different account signed in. **Fixed**: `signOut()` now also calls `detector.disable()`.

### Low

8. A CSV write failure was reported as "No trips to export yet." — the same collapse-failure-into-empty-state bug round 2 fixed for PDF export. **Fixed**: the two cases are now distinguished.
9. The permanent-delete alert still named the backend vendor ("removed from your device and Supabase"). **Fixed**.

### Deliberately deferred from this round

Several real but lower-priority findings are recorded here rather than fixed, to keep this round's changes reviewable: "Tap to classify" opens the Record tab rather than the trip (needs tab-selection plumbing); Low Power mode lets iOS pause a manual recording and `LocationManager` has no pause callback (needs the same treatment `TripDetector` already has); Dynamic Type breaks the fixed-size hero badge and the report-review rows; PDF table cells are truncated by character count rather than measured width, so long Slovenian labels can overlap columns; ~70 user-facing strings are missing from `Localizable.xcstrings`, so a Slovenian user gets a half-English app; the CSV lacks a BOM and uses comma separators, which mojibakes and mis-columns in a Slovenian-locale Excel; and the vehicle selector is still a live-looking control that opens an empty menu when no vehicles exist.

### Confirmed correct from round 4

The `allowsBackgroundLocationUpdates` clearing is complete on every reachable exit path; `energyMode.apply(to:)` in `start()` neither conflicts with `TripDetector`'s separate manager nor can reset the background flag; setting the flag under When-In-Use authorization is coherent (Always is only needed for relaunch-on-location, which the manual path never uses); the `noVehicleHint` → add-vehicle → Start-enables path works end to end and its branch ordering correctly shows one actionable step at a time; and the 12-second `syncIsSlow` task is correctly scoped, cancels cleanly, and can't leak.

## Round 6 review: Score 48.5/100

A sixth reviewer found that round 5's sign-out fix had created a serious regression, and that round 5's password-recovery fix was a dead end. Both are fixed here. Rounds 1–4's work held.

### Critical

1. **Signing out and back in permanently killed auto-detection until app relaunch — while both toggles still read ON.** Round 5 made `signOut()` call `detector.disable()`, which sets `isEnabled = false`. But `startMonitoring()` is reachable from only three places — app launch, the user physically flipping the toggle, and an OS authorization change — and nothing re-armed it on sign-in. Meanwhile `settings.autoDetectEnabled` stayed `true` (and was re-confirmed by the settings pull), so both the Record and Settings toggles rendered ON and the status read "Starting…" forever. Every drive after that went silently unrecorded. The same hole existed in the account-switch branch. **Fixed**: added `TripDetector.resumeIfEnabled()` (re-arms only when the saved preference says on, permission is Always, and monitoring isn't already running) and called it from `initialSync` after the settings pull, so it reflects the account that actually just signed in. Also made the related warn-once flag self-correcting: it now resets whenever a trip commits with a vehicle, since resetting it only in `startMonitoring()` never fired while monitoring was already on.

### High

2. **Round 5's "Forgot password?" sent an email the app had no way to complete.** `resetPasswordForEmail` was called with no `redirectTo`, and the repo had no URL scheme, no `onOpenURL` handler, and no new-password screen — a grep for all of those returned zero hits. The link landed on the Supabase project's Site URL (`localhost:3000` by default), outside the app. The user was confidently told a reset link was on its way, then waited for something that couldn't get them back in — the same lockout as before, plus a false promise. **Fixed**: added `redirectTo` (`milelog://auth/reset`), an `onOpenURL` handler that exchanges the link for a recovery session, a `SetNewPasswordView` that sets the new password, and `updatePassword`/`handleRecoveryLink` on the service. The one step that can't be done from source — registering the URL scheme on the Xcode target and allow-listing the redirect in the Supabase dashboard — is now documented as a numbered setup step in the README, alongside the existing background-mode requirement.

### Medium

3. **One shared `lastSyncFailed` flag let a failed *trips* pull fabricate a "couldn't load your vehicles" error** — replacing the Vehicles tab's onboarding "Add vehicle" call-to-action with a false error, for exactly the first-run user who needs that action. **Fixed**: tracked per collection (`tripsSyncFailed` / `vehiclesSyncFailed`).
4. **Pull-to-refresh re-uploaded the entire local history before downloading anything.** `retrySync()` routed into `initialSync`, which pushes every vehicle and every trip sequentially, one awaited round-trip each, before either pull — a minute-plus of pure re-upload on a year of driving, worst on the slow connection that prompts a refresh in the first place. **Fixed**: `retrySync()` now does only the download half; pushes are still retried by `initialSync` on sign-in and by each mutation's own push.

### Deliberately deferred from this round

Recorded rather than fixed, to keep this round reviewable: the Generate button's result appears below the fold with no other feedback on the report screen; sign-out discards an in-progress trip with no confirmation (round 5 is what made it destructive); `Store.deleteVehicle` guards against hard-deleting the vehicle of an in-progress *auto* trip but not a *manual* one, which can orphan a trip; the biometric-lock toggle is gated on biometrics being enrolled, so un-enrolling leaves the lock permanently on with no way to switch it off; `LocationManager.start()`'s documented "UI should show a warning" return value is discarded by its only caller; "Export 0 trips as CSV" can offer a header-only file; and `retrySync()` is a silent no-op before the first sync has assigned the service.

### Confirmed correct from round 5

The headline worry — that round 5's no-vehicle teardown might disable auto-detect until relaunch — does not hold: `stopUpdatingLocation()` tears down only the standard location service, while significant-location monitoring (a separate service) keeps running and `isEnabled` is untouched, which is byte-for-byte what the FAILED branch has always done and recovered from. The manual-recording yield guard leaves no stranded candidate state and recovers on the next drive. `lastSyncFailed` reset correctly on a subsequent success. `signOut()`'s `disable()` correctly no-ops on the already-discarded trip rather than double-handling or resurrecting it. `ReceiptsSection`'s two chained confirmation dialogs are mutually exclusive by construction and the delete is now real. "Forgot password?" correctly avoids leaking account existence and is gated appropriately — only its downstream completion was broken (High #2).

## Round 7 review: Score 58/100

A seventh reviewer verified round 6's five change areas (three correct, two defective — detailed below) and, while tracing the sign-in path to check one of them, surfaced a much older and much worse defect sitting three lines above it.

### Critical

1. **Signing into an existing account on a new phone silently overwrote that account's saved settings with defaults — locally *and* in the cloud, unrecoverably.** On a fresh install no `settings.json` exists, so `settings` stays at `UserSettings()`. `initialSync` then pushed those defaults before pulling — and `pushSettings` upserts all eighteen columns, replacing the account's real row wholesale — then pulled back exactly what it had just written and saved it. The user silently lost their reimbursement rates (so every future report and Potni Nalog prints wrong € amounts), home/work coordinates (so commute classification stops entirely), the whole company header, the lock threshold, and `autoDetectEnabled`. Trips and vehicles restored correctly around it, making the restore look like it worked. Round 3 removed the vehicle auto-seed for exactly this reason; settings is the single always-present object that had no equivalent protection. It also defeated round 6's own Critical fix on the highest-value path, since `resumeIfEnabled()` guards on an `autoDetectEnabled` that had just been reset to `false`. **Fixed**: added `hasLocalSettings`, true only when a settings file actually decoded from disk. A device without one no longer asserts its defaults — it pulls and adopts the cloud copy, pushing only if the account genuinely has no row yet. The account-switch branch now clears the flag and calls the new `save(pushingSettings: false)`, since its `save()` was pushing the just-reset defaults under the incoming identity too.

### High

2. **`SetNewPasswordView` was a dead end whenever the update failed.** It has no Cancel and `.interactiveDismissDisabled()`, and its only exit was the success branch. But `handleRecoveryLink` has already established a session by then, so `isAuthenticated` is true and there is no sign-in screen behind the sheet — while the error copy told the user to go request a fresh link from exactly that screen. For the two causes the copy named (expired or already-used link) every retry fails identically, so only a force-quit escaped. The same instance of "an affordance that promises recovery and can't deliver it" that round 6 set out to fix. **Fixed**: added a Cancel that signs out and dismisses, returning the user to the screen the copy names; reworded the error so it no longer blames link expiry for what may be a network failure or a server-side password-policy rejection.
3. **No "restoring your session" state — every cold launch rendered the sign-in form first.** `isAuthenticated` starts `false` and is only corrected by a detached Task, and `RootView` branched on it with no third "unknown yet" state, so the first frame of every launch was the email/password form before snapping to the tab bar — a recurring "did I get logged out?" jolt on an app opened in a car. **Fixed**: added `didResolveInitialAuth` and a minimal launch state. (The reviewer also noted a related offline concern — that a failed token refresh is indistinguishable from being signed out, stranding local data behind the auth gate — which depends on SDK behaviour that can't be executed here; recorded as deferred rather than guessed at.)

### Medium

4. **`initialSync`'s first early return left both sync-failure flags untouched and skipped `resumeIfEnabled()`** — so a sync that died at the very first hurdle rendered the confident "No trips yet" empty state, re-creating exactly the regression round 5 fixed, and left auto-detect dead with both toggles reading ON. **Fixed**: that guard now marks both collections failed (when still the current generation).
5. **A failed recovery link did nothing at all — no message anywhere.** The `catch` was empty, so a user who tapped their emailed link and watched the app open saw the same sign-in form with zero acknowledgement, in the one flow where they're already anxious about being locked out. **Fixed**: added an explanatory alert.

### Deliberately deferred from this round
